# demand-scanner (cron, Wednesday)
Follow `routines/agents/_common.md`. Schema and rules: `business/demand/SCHEMA.md`.
Goal: find automation, ETL and full-stack project types that recur (mainly in Israel, also abroad), so Yotam can sell one build to several owners or reuse its code, and rank them by demand and ROI.
1. Sources: use only sources with `status: allowed` in `business/demand/sources.json`, plus any files Yotam put in `business/demand/`. For a source with `status: unchecked`, read its robots.txt and current terms first, record the decision and date in sources.json, and skip it if automated reading is not allowed. Never log in, bypass blocks or buy lists. If there is no allowed data, write that in the report and stop: do not invent listings.
1b. Search phrases: use `business/demand/phrases.json` (Hebrew and English bank by need type). Search only on allowed sources, with those phrases. Tag each listing with `need` (an id from `need_patterns`, if one fits), `signals` (only what the listing's own words show: `existing-spend` = they already pay for a tool or a person for this, `time-loss` = significant lost time stated, `willing-to-pay` = they say they would pay or hire) and `matched_phrases`. Never infer a signal. Expand the bank only with phrases that actually appeared in a real listing (log it in `expansion_log`: phrase, need, date, listing id; no personal data); list phrases with zero yield over 3 runs as drop candidates for Yotam.
2. Collect listing records per the schema (your own one-line summaries, public budgets only, `poster_ref` instead of names). Append to `business/demand/listings.json` (git-ignored); skip ids already present.
3. Run `node scripts/demand-analyze.mjs business/demand/listings.json business/demand/effort.json`. If `effort.json` is missing, report demand only and list the clusters that need Yotam's hour estimates.
4. Report: top 3 recurring types, each with listings, distinct posters, sources, Israel share, budgets per currency, and ROI per build hour when estimates exist. Say what would change the ranking. A type with fewer than 3 distinct posters or 2 sources is "watch", not "build".
5. Owners: listings carry only a `poster_ref` and the listing URL, never names or contact details. The way back to an owner is the platform's own message channel on that listing, used by Yotam himself.
5a. Need ranking: run `node scripts/demand-signals.mjs business/demand/listings.json business/demand/phrases.json business/demand/assets.json`. Highest priority goes to needs with evidence of existing spend, significant lost time, or recurring demand from several owners (priority rule in phrases.json). For each need it names the best existing product/asset and the gap. Flow for a need that matches an existing product (for example a business that manages appointments only by messages and Tori): spot the need > confirm the match (coverage and what is missing, honestly, e.g. WhatsApp reminders are not in Tori) > prepare an offer DRAFT for Yotam with claims only from `products/<slug>.md`. Action `watch` means evidence is thin: report it, do not build an offer. Reach the owner only through the listing's own platform channel, sent by Yotam himself after approving the text.
5b. Reuse: run `node scripts/demand-reuse.mjs business/demand/listings.json business/demand/assets.json business/demand/effort.json`. For each recurring type it names the existing project of Yotam's that already covers most of it (strong / partial / weak), what is already covered and what is still to build. A partial match counts: a similar base with listed gaps is a head start. Put the best base next to every recommendation. Hours saved come only from `reuse_hours_saved` in `assets.json`, which Yotam fills in; if empty, say "needs your estimate". `assets.json` is a draft from Claude (`confirmed:false`): say so, and when a listing uses another word for something an asset does (for example "calendar" vs "booking"), suggest the tag fix instead of ignoring the match.
6. Delivery to offer (when Yotam says a project is finished): add it to `business/demand/delivered.json` (slug, title, category, tags, delivered_on, one-line offer in your own words), then run `node scripts/demand-match.mjs business/demand/listings.json business/demand/delivered.json --outreach business/demand/outreach.json`. It lists candidates (same kind of work, listing not older than 120 days, source allows contact, poster not offered before or opted out) and the skipped ones with the reason. Write one short draft per candidate in the listing's language, only with claims from the delivered project's own notes, and show Yotam the exact text. Nothing is sent by the agent. After he approves and sends a message himself, record the state in `outreach.json` (`sent`, `replied`, `won`, `lost`, `opted_out`). `--d2r` produces private lead records (consent `none`) for `scripts/d2r-ingest.mjs`. Before any email/SMS outreach, a legal check on Israeli anti-spam rules; platform messages are subject to each platform's rules on contacting and off-platform deals.
